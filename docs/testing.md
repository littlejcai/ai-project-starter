# 测试与证据策略

## 分层

| 层次 | 重点 | 时机 |
|---|---|---|
| 单元 | 计算、校验、状态转换 | 规则复杂时先测试再实现 |
| 接口约定 | 输入输出、错误码、运行时校验 | 接口变化时 |
| 集成 | 真实数据库、事务、权限、模块协作 | 每条业务链路 |
| 端到端 | 用户完成核心操作 | 第一条链路开始持续覆盖 |
| 探索/真机 | 体验、设备与平台差异 | 里程碑与发布前 |

不设固定测试数量或覆盖率百分比；按失败后果、复杂度和变更频率分配投入。
需要审查测试预期，而非仅审查测试是否通过。UI 定位围绕可见行为，不依赖易变内部结构。

## 数据与可重复性

测试环境隔离，禁止使用生产数据作为默认夹具。使用固定/可控时间、独立账号和可重置种子数据。
每个用例可独立运行，清理归本用例拥有的数据。数据库事务、唯一约束与并发语义要在真实数据库验证。
第三方依赖可以模拟超时和错误；保留必要真实集成验证，明确环境和范围。

## 红灯、绿灯与重构

新增重要规则测试必须先看到针对缺失行为的失败；例如断言预期容量已满却实际接受。
导入失败、启动失败不证明行为测试有效。修复环境再运行。
示例见 examples/registration/，包含用故意错误实现验证用例可以抓到缺陷的方法。

## 证据

任务中记录：执行时间、代码版本/工作区、命令、环境、结果、相关日志或截图路径。
verify.py 保存每个检查的退出码、耗时、输出及配置快照。没有 Git 提交时如实记录 null/工作区状态。
报告只证明被配置命令的执行结果，不自动证明用例充分、代码未变或真机通过。
截图和日志应脱敏；需要归档的证据存放在项目认可的位置，原始 artifacts/ 默认忽略。

## 含模型输出的产品（按需）

结构、权限、超时与异常使用确定性测试；生成内容的质量另用固定样本、评分规则和人工抽查评估。
不要对随机生成文本直接做完全字符串相等断言；记录模型/提示版本和样本范围。
