# 测试与证据策略

## 分层

| 层次 | 重点 | 时机 |
|---|---|---|
| 单元 | 计算、校验、状态转换 | 规则复杂时先测试再实现 |
| 接口约定 | 输入输出、错误码、运行时校验 | 接口变化时 |
| 集成 | 真实数据库、事务、权限、模块协作 | 新增或改变相关依赖、数据流或语义时 |
| 端到端 | 用户完成核心操作 | 第一条链路开始持续覆盖 |
| 探索/真机 | 体验、设备与平台差异 | 里程碑与发布前 |

不设固定测试数量或覆盖率百分比；按失败后果、复杂度和变更频率分配投入。
需要审查测试预期，而非仅审查测试是否通过。UI 定位围绕可见行为，不依赖易变内部结构。

## 范围与停止条件

先选择能验证本次验收和受影响行为的检查，并遵守项目既有必需检查、CI 与发布要求。简单文案/文档修改不强制新增单元测试；复杂规则、重要状态与缺陷回归保留有意义的行为测试。
开发中运行相关用例；新变更使旧证据失效、检查失败或出现具体未解决风险时，补充或扩大到受影响模块/集成范围。修改公共接口、依赖、构建或数据库语义时评估调用方和必要完整回归。
当前版本的验收证据充分、必需检查通过且相关阻塞项已处置后停止。不得为了确认同一结论无依据地重复全量测试，也不能以节省成本为由绕过既有门禁。
只改与运行行为无关的说明文字后，可沿用仍适用的代码测试证据，并检查改动的文档结构/链接；代码、配置或环境变化需重新判断证据适用性。
缺少环境时记录未执行与影响，不宣称验收完成。修正测试预期必须有业务规则或测试错误依据，不为通过而删除断言或跳过要求。

## 数据与可重复性

测试环境隔离，禁止使用生产数据作为默认夹具。使用固定/可控时间、独立账号和可重置种子数据。
每个用例可独立运行，清理归本用例拥有的数据。数据库事务、唯一约束与并发语义要在真实数据库验证。
第三方依赖可以模拟超时和错误；保留必要真实集成验证，明确环境和范围。

## 红灯、绿灯与重构

新增重要规则测试必须先看到针对缺失行为的失败；例如断言预期容量已满却实际接受。
导入失败、启动失败不证明行为测试有效。修复环境再运行。
测试代码使用业务选定的语言与框架；脚本自检不替代这些业务用例。

## 报告与证据管理

| 内容 | 保存位置与用途 |
|---|---|
| 验收结论 | 当前任务的验证表，随 Git 提交；引用关键运行和证据，不抄全量日志 |
| 自动检查摘要 | 每次运行的 artifacts/<run-id>/summary.md，便于查看和关联版本；CI 默认归档 14 天 |
| 原始执行记录 | 同目录 report.json 与各检查日志，本地保留、默认 Git 忽略；排障或长期验收需要时脱敏归档 |
| 人工、浏览器、真机结果 | 任务内记录操作、环境、结果和截图/录像位置，单独判断是否满足验收 |

使用 `python3 scripts/verify.py --profile current --task FEAT-001` 可关联已有任务；不关联时省略 --task。脚本不会修改任务状态或自动判定业务验收。
summary.md 只列任务、版本、阶段/范围、环境、检查状态、退出码和耗时，不复制命令参数、配置或原始输出；report.json 保存详细命令、配置快照和工作区状态。失败及配置错误也生成记录，非法命令行参数在执行前退出。
任务保存最终有效结论和必要失败/修复证据即可。报告的命令数不是用例数，不能据此计算覆盖率；报告通过也不证明测试充分或真机通过。
多端项目在任务验证表注明后端/Web/小程序范围，分别举证；不要将某一端结果视作全端通过。Git 提交带未提交改动时标明；重要验收固定版本或保存差异，摘要不保存代码快照。
排障先用 verify.py --report RUN_ID 定位失败检查，需要时再展开日志，命令见 [按需读取](verification-setup.md#按需读取)。
CI 摘要的保留期可以按项目调整，报告需连同 workflow 总状态阅读；组合检查中的静态失败会进入摘要并使整体失败；框架回归单独运行，其失败也不能被摘要绿灯覆盖。CI 默认不上传 report.json、配置快照、原始日志或截图。
发布、重要缺陷等需要长期追溯时，将必要脱敏证据存入项目约定的持久位置，并在任务/发布记录注明位置、责任人和保留期限；不要只留下会过期的 CI 链接。普通中间运行无需逐一进 Git，原始文件清理前先保留仍被引用的证据。

## 含模型输出的产品（按需）

结构、权限、超时与异常使用确定性测试；生成内容的质量另用固定样本、评分规则和人工抽查评估。
不要对随机生成文本直接做完全字符串相等断言；记录模型/提示版本和样本范围。

## 反例、不变量与受控故障

先从业务规则定义前提、成功后的结果和不变量，明确检查边界（如事务提交后）。字段校验不能替代业务一致性。
针对关键规则选择相关反例：容量边界、重复、乱序、并发、未授权写入、依赖失败与部分成功。
按风险使用参数化/属性测试扩大输入覆盖；性质本身也需业务依据，不能从错误实现推导。
必要时在隔离测试环境用故障注入检验断言能否发现问题；不要求每次变更都运行变异测试或引入新工具。
纯函数规则测试不能单独证明真实数据库的事务或并发安全。
对抗性审查同时检查测试预期、真实依赖覆盖与证据范围，按 [review.md](review.md) 记录。保留现有快速/完整检查，不引入 AI 自评分自动放行。
