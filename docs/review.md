# 对抗性审查流程

目标：在限定范围内找到有依据的失败条件，帮助正确交付。审查针对方案和实现，讨论具体证据。
风险分级见 [开发原则](principles.md)；结果写在当前任务的审查段落，必要时链接补充材料。

## 触发与输入

- 低风险：直接核对变更与预览/回归即可，不强制单独生成审查报告。
- 普通风险：实现后一次针对性审查；方案有重要未知时先验证。
- 高风险：方案确认前和实现后分别审查。输入包括目标、约束、规则、不变量、相关代码/接口/测试、变更版本及已有证据。

独立审查时先阅读需求、约定和实际差异形成判断，再对照开发者的结论；可以读取其设计理由，但不能只依赖完成摘要。
工具条件与授权允许时，可由另一个会话、模型或人执行重要审查；默认不强制多 Agent。角色切换或更换模型不保证独立性或正确性，记录实际执行者和独立程度。

## 使用子 Agent 时

按 [协作约定](agents.md) 传递最小交接包，可使用 [委派提示](../prompts/subagent-review.md)。子 Agent 默认只读业务文件，结果返回主 Agent。
主 Agent 记录采纳/驳回/待确认及依据，修复后核对目标版本；新变更不得直接沿用旧审查结论。
工具不可用时如实记录降级方式，自审不称为独立审查；最终集成验证仍由主 Agent 负责。

## 执行步骤

1. 确认范围、风险、审查阶段、代码版本和未覆盖部分。
2. 复核目标与关键假设：当前方案真的解决问题吗？依据是否成立？是否有更简单的可行方案？
3. 找反例：边界输入、资源归属、重复/乱序/并发、部分成功、超时和恢复；仅展开与本次相关的维度。
4. 检查测试本身：预期是否源自规则？错误实现能否仍通过？模拟与真实集成的边界是否明确？
5. 尽可能以现有代码路径、最小复现或测试验证发现。不能验证时标明风险与所需条件。
6. 对问题分类、处置；修复后复查修复及受影响范围，记录完成结论。

审查阶段默认不直接改业务实现；如任务包含修复，则在记录发现后进入修复阶段。需求冲突交给相应业务负责人裁定，不擅自改规则让测试变绿。

## 结果格式

先记录阶段、审查者/方式、提交或工作区、已审查范围、未覆盖范围，再记录发现：

| ID | 类型 | 严重程度 | 位置/规则 | 触发条件与影响 | 证据或验证方法 | 处置与复查 |
|---|---|---|---|---|---|---|
| R-001 | 已确认缺陷/待验证风险/非阻塞建议 | 严重/主要/次要 | 文件、函数或规则 | 具体描述 | 实际证据或待验证步骤 | 负责人、动作、结果 |

类型表示证据状态，严重程度表示后果，两者分别判断。
严重：越权、资金/数据损失、核心流程不可用等；主要：重要验收不满足或业务错误；次要：影响有限、存在可靠替代路径等。
阻塞与否看本期验收和后果，不仅看标签。风格偏好不作为阻塞缺陷；重大但未验证风险必须得到验证或由有权负责人明确处置。

## 停止与交付

约定范围已检查，阻塞问题已解决或有权负责人已明确处置，相关验证充分，即结束审查。
接受未解决风险须记录负责人、理由、后续动作及已有授权，不能由 AI 自行勾选为已接受。
允许结论为“在已审查范围内未发现问题”，同时列明范围与限制；不要求每次找出固定数量问题。
修复后只复查修复与影响范围；新证据或范围扩大才重新展开。不要为了追求绝对零风险反复全文审查。
没有执行某项验证就写未执行；自动检查通过不表示本审查或真机验证已完成。脚本仅检查客观事实，不让 AI 自评分作为自动放行依据。
