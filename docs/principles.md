# 六项开发原则

本页是面向本框架的实践约定。原则用于减少错误与返工，按风险使用；不要求每次任务输出长篇推导。结论、依据、假设和验证结果应简短、可核对。

## 1. 第一性原理：从目标与约束推导方案

触发：新项目、重要功能、关键架构选择、连续返工；已有结论仍有效时引用即可。

回答五个问题，写入产品定义、当前任务或重要决策记录，不重复建一份报告：

1. 用户真正需要什么可观察的结果？区分目标与指定的实现手段。
2. 哪些是已经核实的事实、已确认规则或硬约束？标明来源与适用条件。
3. 哪些只是当前假设？标明未知，不把模型推测当成事实。
4. 满足当前目标的最小可行方案是什么？优先考虑复用已有能力。
5. 哪项假设若错误会导致最大损失或返工？用什么小实验优先验证？

例：用户想让 AI 自动安排聚会。目标可能是找到共同空闲时间；时间交集可由规则计算，AI 只负责自然语言输入。是否需要 AI 参与匹配，应由需求和实验决定。
边界：尊重用户已经明确的约束，不擅自改范围；复用成熟标准和已验证结论，不从头重造基础设施。普通文案修改无需重新推导。

## 2. 对抗性审查：主动寻找失败条件

触发：普通业务完成后做针对性审查；高风险任务在方案与实现阶段分别审查。
从需求、约定、实际变更和测试找反例，检查遗漏、权限、重复请求、乱序、并发和依赖失败等与本次相关的场景。
输出问题的位置、条件、影响、证据和处置；区分已确认缺陷、待验证风险、非阻塞建议。允许未发现问题，不设问题配额。
完整执行方法见 [审查流程](review.md)。审查不自动要求多个 Agent，也不替代真实测试。

## 3. 简单设计：KISS / YAGNI

默认应用于设计与实现。优先满足已经确认的当前需求，引入依赖、抽象或扩展点时能说明本期用途。
比较最小方案与主要替代方案的实现、维护和迁移成本；没有真实需求时，避免预建多租户、插件系统或通用流程引擎。
简单不等于省略必要的鉴权、数据一致性、测试或可维护性；为未来修改提供合理模块边界，必要时重构。

## 4. 契约与不变量：明确必须成立的条件

除输入输出字段外，写清操作前提、成功后的结果，以及在约定边界上必须成立的业务条件。
例：已确认报名人数不超过容量；同一用户在同一活动最多一个有效报名；未授权操作不改变报名数据。
在当前任务中引用业务规则，按技术栈落实到校验、数据库约束、事务和测试。说明不变量检查是在事务提交后、接口返回后还是最终一致性窗口结束后。
静态类型和单个示例都不能单独保证这些条件；不强制引入形式化验证工具。

## 5. 证伪与最小实验：寻找能推翻假设的证据

对高影响、低把握的假设，事先明确实验和判定标准，得到证据后再决定是否扩展实现。
针对关键规则，问“如果代码在这个地方出错，哪个测试会失败？”需要时补边界、属性测试或受控故障注入。
在隔离测试环境验证超时、重复、乱序等故障；不要直接向生产注入故障。
测试先因缺失行为失败，再通过，仍沿用 TDD 小步循环。不要只证明正常例子能跑通，也不要为每个低风险修改引入重型测试工具。

## 6. 小批量与可回退变更

每个任务交付一条可验收的业务链路，减少无关重构；提交尽量可以独立理解和验证。
易回退的实现自主推进；难回退的架构、数据迁移和外部副作用，需要提前明确验证、恢复或补偿办法，沿用用户已有授权。
代码回滚不等于数据恢复或外部操作撤销。关键假设改变时记录重新评估条件，避免已确认方案被无理由反复推翻。

## 如何选择深度

| 风险 | 判断示例 | 最小动作 |
|---|---|---|
| 低 | 不影响规则的文案、布局、展示 | 一句影响判断，预览或相关回归；不强制独立审查报告 |
| 普通 | 单一业务功能、常规接口 | 目标和关键假设、相关规则及测试、一次针对性实现审查 |
| 高 | 权限、资金、并发、数据迁移、核心架构，或高损失且未验证的依赖 | 显式假设和不变量、方案与实现两次审查、必要失败/恢复验证 |

按后果和不确定性判断，不按代码行数。任务扩大或出现新事实时更新风险及理由。
已确认硬约束与正确性优先于少写代码；验证投入随风险增加；只记录影响决策的证据。审查结束条件见 [review.md](review.md)。

## 参考与适用说明

- [YAGNI：Martin Fowler](https://martinfowler.com/bliki/Yagni.html)：避免提前实现猜测的能力，同时保持代码可修改。
- [Google 代码审查](https://google.github.io/eng-practices/review/reviewer/looking-for.html)：功能、并发、复杂度与测试质量。
- [Eiffel 契约式设计](https://www.eiffel.org/doc/solutions/Design_by_Contract_and_Assertions)：前置条件、后置条件与不变量。
- [Google 小规模变更](https://google.github.io/eng-practices/review/developer/small-cls.html)：使修改更易理解与审查。

五问、风险分级和本框架中的执行方式是工程实践建议，不是这些来源共同定义的一套标准，也不保证固定比例的效率提升。
