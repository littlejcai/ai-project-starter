# 开发流程

按当前任务选择对应路径，不要求每次执行完整启动流程；已确认结论直接引用。

## 新项目初始化

完成轻量 PRD 与验收例子，验证高风险能力，确定最小技术基线，创建第一条完整业务任务。
需求范围未定时允许原型探索，标明实验内容，不一次性冻结全部接口或编写全项目测试。
使用 [第一性原理](principles.md) 明确关键假设、硬约束与最小实验，将结论写产品定义或决策。选型后按真实模块建立源码、测试、契约和适配目录，不保留与所选技术栈无关的占位层；同时补运行说明与 [真实检查命令](verification-setup.md)。
只详细拆解当前和下一里程碑；更远阶段先记录用户结果、依赖与待决问题。阶段配置、推进与验证按 [配置指南](verification-setup.md) 执行。

### 界面与品牌基线（按需）

初始化时确认是否存在用户界面、实际界面交付，以及可沿用的品牌、设计系统、设计稿或组件库。按以下最小规则处理：

- 后端、CLI、内部脚本等无用户界面项目，不创建体验文档；短期界面实验可以先在产品或任务中记录假设。
- 有实际界面交付时，在实现前创建一份 `docs/experience.md` 作为体验事实源；若已有成熟规范，只记录其地址、版本、适用边界和项目差异，不复制整套内容。
- 单一体验基线只保留：目标体验与品牌表达、核心用户旅程与信息架构、关键页面状态、视觉/交互原则与语义令牌、平台差异/可访问性、原型或资产引用、可观察的验收方式。
- 只有多端或多品牌需要独立治理、多人长期并行维护，或单文件已明显妨碍定位时，才拆分为品牌与 UX/UI 文档；具体文件名和目录按项目实际结构决定。

体验文档约束实现、审查和验收，但其存在不代表界面通过。界面行为仍须使用目标浏览器、开发者工具或设备通过可见操作验证；截图和设计稿是证据或输入，不自动成为运行事实。

## 业务功能与重要修复

1. 从任务的文件/符号、规则和测试引用定位，核对有效性后确定验收、影响范围与风险；任务大小以一条完整可验收的用户行为为宜。
2. 补齐本次涉及的数据、接口、权限、状态和异常约定，引用已有规则。高风险先按 [审查流程](review.md) 审查方案及恢复/补偿路径。
3. 列相关场景；复杂规则、重要状态先用行为测试确认预期失败，再实现、通过与重构，细则见 [测试策略](testing.md)。缺陷先复现，重要缺陷补回归用例。
4. 根据变更运行相关检查。涉及接口调用、持久化、事务或权限时及时验证对应真实集成；界面行为用浏览器/开发者工具验证，平台相关能力按需补真机证据。
5. 普通与高风险任务审查实现和测试。主 Agent 在已有授权内处置发现并继续修复、验证，审查阶段不自动构成用户审批关卡。
6. 验收满足且必要检查完成后同步受影响文档与任务记录，执行已授权的提交/推送；合并和发布仍遵守项目既有检查与授权要求。

有可独立完成的子任务时按 [协作约定](agents.md) 判断是否委派。风险决定审查深度，不固定要求 Agent 数量。
范围扩大或出现新事实时重新评估风险；方法取舍查 [原则说明](principles.md)。

## 简单局部修改

文案、低风险样式、局部文档修正：检查相关位置及影响，直接修改并执行针对性验证。文档检查链接，界面修改做预览；遵守现有必需检查。
不强制新建任务、完整计划、单元测试或独立审查报告。若发现权限、业务规则或数据行为受影响，转入上面的业务流程。

## 按需记录

任务模板仅保留目标、验收、变更、证据与交接，额外记录按触发条件添加：

- 重要需求、架构或反复失败：记录假设、约束与实验结论；高风险补不变量和恢复/补偿方案，方法见原则。
- 实际界面交付：引用体验事实源及适用版本；仅在触发条件成立时创建或拆分，不为填写模板而扩写。
- 新增重要行为测试或修正预期：按测试策略记录首次行为失败、通过结果或预期变更依据。
- 普通/高风险审查：使用审查标准的版本、方式、覆盖范围、发现与处置格式；无发现简记范围及限制。
- 委派子任务：按协作约定记录分工、范围/工作区、版本、证据及主 Agent 处置。

## 停止与交接

测试范围和停止条件以 [测试策略](testing.md) 为准，审查停止条件以 [审查流程](review.md) 为准；证据未失效时不重复同一检查。
遇到阻塞，记录已完成、缺失条件和可继续工作；不要用环境失败冒充行为测试失败，也不要为绿灯降低要求。
只有跨任务进度变化才更新状态页。发布任务查 [发布清单](release.md)，不以代码生成或模板检查通过宣称业务交付。
评估流程时可记录耗时、返工、遗漏与可获取的 AI 用量；不要求日常小修改填写效率报表。
