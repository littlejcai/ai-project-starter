# 开发流程

## 项目启动一次

完成轻量 PRD 与验收例子，验证高风险能力，确定最小技术基线，创建第一条完整业务任务。
需求范围未定时允许原型探索，但标明实验内容；不一次性冻结全部细节。
对新项目和重要决策使用 [第一性原理五问](principles.md)：目标、事实/约束、假设、最小方案、关键实验。结论直接写产品定义或决策，已验证信息引用即可。
优先验证错误后代价最大的假设；简单设计保留必要的可维护性，避免提前实现猜测能力。

## 每个功能循环

1. 读取入口、当前任务及相关资料，确认验收规则、影响范围和风险等级及理由。
2. 补齐当前功能的数据、接口、权限、异常约定与不变量；界面准备简单状态稿。高风险任务按 [审查流程](review.md) 先审查方案，明确恢复/补偿路径。
3. 列测试场景。对复杂规则先写一条测试，运行确认预期失败，再实现通过。
4. 继续小步测试、实现、重构；每一步运行相关快速检查。
5. 尽早连接真实接口和隔离测试数据库，检查完整数据流。
6. 有界面就通过浏览器或开发者工具执行主流程，按风险补失败和权限场景。
7. 普通和高风险任务按 [审查流程](review.md) 审查实现及测试；低风险做简短核对和预览/回归即可。记录缺陷、待验证风险、建议及证据，修复后复查相关影响。
8. 更新任务、文档、验证证据和状态后提交；合并前执行约定回归检查。

任务大小：一次能验收的完整用户行为；避免一次包揽整套后端或所有页面。
默认单 Agent。适合独立审查时按 [协作约定](agents.md) 委派，复杂任务才考虑专项分工；风险分级决定审查深度，不强制 Agent 数量。
委派固定目标版本和文件范围；主 Agent 处置发现、整合变更，并在最终版本验证后交付。共享文件或不稳定接口先串行收敛。
低风险文案/布局变化可用预览与相关回归，不强制单元测试或独立审查报告。
风险按后果和不确定性判断，范围扩大时重新评估。原则冲突按 [原则说明](principles.md) 处理。
审查范围已检查、阻塞问题已处置、相关验证充分后结束，避免无新增证据的重复全量审查。

## 发现问题

复现并记录预期与实际 → 重要缺陷先补可复现的回归用例 → 修复最小原因 → 检查邻近影响。
测试因环境错误失败时先修复环境，不把它当作业务行为已被覆盖。
需求变化可改变测试，但需同时更新规则并记录理由。不能为绿灯降低检查要求。

## 交付与效率

记录任务开始/完成时间、返工轮次、验收后缺陷、AI 用量（可获取时）。先试跑三个功能再调整流程。
遇到阻塞记录已经完成、阻塞原因、可继续的工作；已获授权的可逆步骤持续推进。
发布在自动检查后另走 release.md；不以“代码已生成”或“demo 通过”宣称交付。
